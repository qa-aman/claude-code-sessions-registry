# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

`ccs` (Claude Code Sessions) is a local session manager: name, list, and resume Claude Code sessions across terminals without the `/resume` picker. Pure bash + python3, no daemons or database.

The repo has **only three tracked files**: `README.md`, `CHANGELOG.md`, and `claude-sessions-registry-bootstrap.html`. There is no build, no lint, no test suite, no package manager, no CI. The "app" is distributed as a single HTML page a user hands to a fresh Claude Code session.

## The critical architecture fact: source lives inside the HTML

There is no standalone `ccs` script file in this repo. The **canonical source of every runtime artifact is an HTML-escaped `<pre>` block** inside `claude-sessions-registry-bootstrap.html`. The installed files (`~/.local/bin/ccs`, the statusline script, `~/.claude/settings.json` merges) are generated by copying those blocks out. Key blocks, by `<pre id="...">`:

- `ccs-source` (~line 262) — the full `ccs` bash CLI. **This is the real program.** Edit here.
- `bootstrap-prompt` (~line 76) — the paste-into-Claude prompt that performs the install. It embeds its own copy of the install logic.
- `ccs-install` (~line 770) — manual install commands.
- `statusline-script` / `statusline-settings` / `statusline-merge` — statusline setup.
- `cleanup-settings` / `cleanup-merge` — the `cleanupPeriodDays` settings merge.
- `registry-template` — the per-project markdown template (also embedded again as `REGISTRY_TEMPLATE` heredoc inside `ccs-source`).

**HTML-entity gotcha:** because these scripts live inside HTML `<pre>` tags, every `<`, `>`, and `&` is written as `&lt;`, `&gt;`, `&amp;`. When editing a `<pre>` block you must keep that escaping (e.g. a bash heredoc reads `&lt;&lt; 'PYEOF'`, a redirect reads `&gt;`). When reasoning about behavior, mentally un-escape first. Getting this wrong silently corrupts the shipped script.

**Duplication to keep in sync:** the same logic often appears in three places — the `ccs-source` block, the `bootstrap-prompt` block, and `README.md`. A change to command behavior or the settings a user must set usually has to land in all three. The `cleanupPeriodDays` feature is the reference example (touched bootstrap, statusline settings, and README).

## How `ccs` works (the model)

Global state is `~/.claude/named-sessions.json`: `{ "sessions": { "<name>": { id, description, project, project_path, pid, created_at } } }`, keyed by user-chosen name. `ccs` derives everything else at read time from two Claude Code files it does not own:

- `~/.claude/sessions/<pid>.json` — maps a PID to its `sessionId` and `cwd`. This is how `ccs add <name> <pid>` resolves a statusline PID to a resumable session ID and project path.
- `~/.claude/history.jsonl` — scanned once per command for message count, last-used timestamp, and the first `display` message (used as an auto-description).

`ccs add` accepts either a PID (numeric, ≤7 digits → looked up in `sessions/`) or a full session ID. On first `add` in a project it auto-creates `<project>/.claude/claude-sessions-registry.md` from the embedded template.

`sync_md` (run after every mutating command) rewrites each project's Registered Sessions table by regex-replacing everything between `## Registered Sessions` and the next `\n---`. Projects are discovered from the `project_path` stored on each session entry. Never hand-edit that table; it is regenerated.

`ccs open <name>` runs `claude --resume <id>` and therefore must be run **outside** an active Claude Code session.

Each command is a `case` branch in `ccs-source` that shells into an inline `python3` heredoc for the JSON/history work.

## Conventions

- Dates are **DD-MM-YYYY** everywhere (Python `strftime("%d-%m-%Y")`, docs, output). Keep it.
- Session names: lowercase kebab-case, case-sensitive.
- Commit messages: lowercase, imperative ("add ...", "fix ...", "harden ..."), optional type prefix.
- The registry markdown and JSON contain no secrets (no tokens, no transcripts) — safe to commit.

## Verifying a change

There is no test harness. To check an edit to `ccs-source`, extract the block's text, un-escape the HTML entities, write it to a file, `chmod +x`, and run commands (`ccs list`, `ccs pids`) against your real `~/.claude` state — or dry-read the python heredocs. Confirm the three-way duplication (source / bootstrap-prompt / README) stays consistent before committing.
